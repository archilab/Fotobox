# Privacy and consent requirements (engineering draft, not legal advice)

1. The keyboard kiosk (ADR-020) shows the operator's consent notice and records the participant's confirmation with the notice's version. The notice is a draft until the operator has had it reviewed, and a key press shows the notice was confirmed, not who confirmed it or their age. The command line CLI remains a developer tool that **cannot display or obtain user consent**. Operate it only with synthetic media or participants who received notice and explicitly consented via a documented outside process.
2. Two separate purposes: processing image for current strip; reuse in temporary pool. Recording a photo does **not** itself establish consent, and pool reuse should not be forcibly bundled with strip generation. The kiosk asks for pool use as a second, separate question that states the exact end time; ESC leaves the photo out of the pool and changes nothing else. The pool copy is deleted at the time shown at the latest (ADR-024). Other visitors see an AI strip with that person in it, never the photo itself.
3. Later touchscreen must use actively selected, understandable consent UI, accessible notice, refusal path, versioned policy, and a demonstrable revocation mechanism.
4. Provisional pool TTL 24h, editable; current demo uses 1h retention for non-pool portrait. These are engineering defaults, not approved privacy schedules. A strip expires with the portraits it contains, and the server deletes expired files automatically (ADR-013). Frames in `jobs/` exist only while a job is active, and are deleted when it ends, is cancelled or is withdrawn. Backups of the server machine are not covered, so exclude the storage folder from them.
5. Expired/revoked items must be excluded from matching immediately, even if file deletion is pending; wipe original, intermediates, result copies, queue payloads and relevant backups according to policy. The operator gives each participant a one-time withdrawal code and runs `admin withdraw`, which deletes their images and every strip containing them on the server (ADR-016). A strip already saved on a client, and backups, are not covered. Losing the code is not final: the operator can also withdraw by session id, if the participant's session can be identified from outside records.
6. No public image gallery, digital user retrieval or remote download; API `result` is an **internal client endpoint** in MVP.
7. Minimize logs; do not collect names, face embeddings, GPS or identity assertions. Consent artifacts must not contain photos unless necessary. The audit trail holds opaque ids only and has no retention limit yet: decide one before public use.
8. Seed images require appropriate rights and permission, attested with a reference at import; label mock/test artifacts.
9. Public exhibition requires controller's GDPR assessment, access control and tested deletion and withdrawal paths.
10. Social presence (ADR-023): other boxes are told that someone is taking a photo at a named place, only after consent is recorded and only while the session lasts, and that a photo was taken in the last 3 minutes. No image, name, session id or address is sent. Ages are hidden by default (`PHOTOBOX_PUBLIC_ACTIVITY_DETAIL=coarse`). The events are deleted after an hour. The consent notice must say this before more than one box is in use; the example notice does. "Someone left a photo for you" appears only while a visitor's pool portrait with valid pool consent exists, never for seeds.
