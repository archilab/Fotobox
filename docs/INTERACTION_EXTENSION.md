# CONNECTED PHOTOBOX — Social Presence & Communication Extension

**Version:** 0.3  
**Document type:** Implementation instructions for Claude Code  
**Extends:** Connected Photobox Development Starter Kit V0.5 and Social Presence & Communication Extension V0.2  
**Status:** Extension specification; implement incrementally, with messaging gated behind real paired sessions

> **Adopted with changes** in ADR-023 and ADR-024 (`docs/DECISIONS.md`): the booth already has a screen, presence is shown on the kiosk's idle screen, live matching across boxes is brought forward, and the V0.2 document referred to below does not exist. Where this spec and the ADRs differ, the ADRs apply.

## 1. Instructions to Claude Code

Read root `CLAUDE.md`, `docs/ARCHITECTURE.md`, `docs/API.md`, `docs/DATA_MODEL.md`, `docs/PRIVACY.md`, `docs/SECURITY.md`, and milestone documentation before changing the project. This document **supersedes the interaction-design direction** in V0.1/V0.2 when they conflict. It does not supersede the core camera-to-server pipeline.

**Primary design direction: SOCIAL / COMMUNICATIVE.** Build an interface that explicitly tells visitors what is happening at other Photoboxes, how recently a photograph was taken, whether they can participate in a real-time connection, and what they should do next. Use large, readable typography, clear status indicators, location names, concise calls to action, and brief animated transitions. Abstract generative visuals are secondary to legible information.

**Critical scope constraint:** The current physical MVP has **one Raspberry Pi and a standard USB webcam only**. There is **no touchscreen, no installed presentation screen, no speaker and no printer** in the base V0.5 phase. This V0.3 extension adds an **optional USB microphone and Enter-key push-to-talk** for a later incremental prototype; it must not become a dependency of the base camera-to-server workflow. Implement the text-message visualization in a developer browser preview until a screen is installed. Do not make absent peripherals runtime requirements. Do not start automatic capture, record people in the background, or infer visitor presence from a heartbeat. A CLI test trigger stands in for the eventual user action.

After inspecting the repository, propose changes and implement the smallest independently testable milestone. Keep existing working endpoints compatible when feasible. Write tests and update specifications. Do not report an untested feature as working.

## 2. Experience goal

The Photobox is a **distributed social invitation**. A visitor should immediately understand:

1. **Where** an activity is taking place (when a location is approved for display).
2. **What** is happening: another box is connected, someone started a session, a photo was taken, or a portrait from earlier is available.
3. **When** the activity happened: live, just now, minutes ago, or earlier — only when supported by timestamps.
4. **What happens if I take a picture**: an attempt to connect to another live participant or, when unavailable, a match with a previously authorized portrait.
5. **What happens next**: matching, generation, ready, and (in a later phase) printing.

The invitation must remain friendly and accessible rather than technical. Text messaging is the primary interaction language. Do not suggest that strangers are watching one another or communicating by live video. No direct inter-box live video or audio feed is allowed. Optional participant communication is **text-only**, generated by local speech-to-text on the sending Raspberry Pi and delivered only to active matched boxes.

## 3. Truthful network status model

Maintain **device state**, **user/session activity**, **portrait availability**, and **matching state** separately. Never infer human presence from device connectivity.

| Condition | Meaning | Public presentation |
|---|---|---|
| `device_online` | Remote Pi is connected | "Berlin Photobox is connected." Not "someone is there." |
| `session_started` | A visitor explicitly began an interaction | "Someone is active in Berlin." Only while their session is active. |
| `photo_captured` | A visitor completed an authorized capture | "A photo was just taken in Berlin." Only within the configured recent interval. |
| `live_match_available` | Two eligible overlapping sessions can be paired | "Someone is ready for a shared photo." |
| `pool_portrait_available` | Valid consented earlier photo exists | "A photo from earlier is waiting to join yours." Never claim the person is present. |
| `live_match_created` | Two active sessions matched | "You're connected with Berlin!" |
| `pool_match_created` | Active photo matched with an earlier portrait | "Your photo meets someone from earlier." |
| `generating` | Server is making image series | "Your shared photo is taking shape…" |
| `result_ready` | Digital file is produced | "Your photo strip is ready." Current MVP: technical browser preview only. |
| `printing` | Later printer phase | "Printing your photo strip…" Do not expose until actual hardware integrated. |
| `device_offline` | Remote box cannot be reached | "Berlin is currently offline." |

State expires by TTL. Network aggregation must not imply a live human when only old events remain. Display location labels from an admin-configured public-safe label, not raw device or IP names.

## 4. Screen hierarchy

Prioritize one main invitation at any time:

**Header:** `CONNECTED PHOTOBOX` + small overall connection status.  
**Hero:** one actionable social message (large type; one or two lines).  
**Explanation:** a short second sentence about the potential encounter.  
**CTA:** `TAKE A PHOTO` when capture is enabled (later UI phase). For the current browser simulator show `SIMULATE PHOTO` clearly tagged developer-only.  
**Locations panel:** concise status rows or tiles for configured remote boxes.  
**Footer:** succinct privacy explanation and link to information when a real user-facing screen exists.

Important: do not display a clickable "Take a photo" button in the physical MVP unless the hardware interaction is actually implemented. The browser simulator may contain working simulation controls.

### Example visual status tiles

- `ESSEN — Your box — Ready`
- `BERLIN — Someone active — LIVE`
- `LONDON — Photo taken 2 min ago — RECENT`
- `OTHER LOCATION — Connected — ONLINE`

Limit the initial visible network panel to approximately 3–5 locations; summarize more as `+N other locations`. Show statuses in priority order: active live > recent photograph > eligible earlier portrait > online-only > offline. Avoid intrusive granular timestamps for small audiences; exact times are configurable and normally hidden.

## 5. Message catalog and priority rules

All copy must be stored in a localization-ready message catalog, not embedded in state-handling code. Initial language English; allow later German translation. Tokens like `{location}` and `{elapsed}` must be escaped safely and supplied only by trusted, sanitized data.

| Priority | Trigger | Hero message | Supporting text | UI treatment |
|---|---|---|---|---|
| P0 | Current box unavailable | "This Photobox is temporarily unavailable." | "Please try again shortly." | Clear neutral error |
| P1 | Live match established | "You're connected with {location}!" | "Two people, one shared photo." | Strong short transition |
| P2 | Remote eligible session is active | "Someone is taking a photo in {location}." | "Take yours now for a chance to connect." | Distinct LIVE status |
| P3 | Photo was captured elsewhere recently | "A photo was just taken in {location}." | "Add yours to the story." | RECENT, not LIVE |
| P4 | Valid earlier pool portrait exists | "Someone left a photo for you." | "Take yours to create an unexpected encounter." | EARLIER portrait label |
| P5 | Other boxes online only | "Other Photoboxes are connected." | "Take a photo to start an encounter." | ONLINE, no human claim |
| P6 | Nothing remote available | "Your next encounter starts here." | "Take a photo to begin." | Neutral invitation |

The main message should be based on the **current real server state**. Message transitions are driven by events, not random assertions. Avoid false urgency: no fake countdown, artificial scarcity, or "someone is waiting" unless another active participant truly is.

**Example alternate copy bank:**

- LIVE: "Someone in Berlin is ready to connect." / "Another person is at a Photobox right now."
- RECENT: "Berlin just sent a photograph into the network." / "A new photo arrived moments ago."
- EARLIER: "Meet someone who was here earlier." / "A portrait is available for a shared photo."
- CALL TO ACTION: "Join the picture." / "Take a photo and connect." / "Be part of the next encounter."
- MATCH: "Two places. One photo strip." / "Your encounter has begun."

These messages are examples, not new server states.

## 6. Displayed activity: what and when

- **Live state:** derives from an explicitly started session with a valid lease and recent heartbeat; automatically expires when session completes, aborts or lease ends.
- **Recent-photo state:** derive from consented capture-completion event; configurable period (suggest 3 minutes for prototype testing, not a final production policy). Visibility of recent activity is independent of whether the image can still be matched.
- **Earlier-portrait state:** derives exclusively from current pool eligibility and consent. Never display raw portrait thumbnails or face silhouettes extracted from user imagery.
- **Offline state:** derive from authenticated device-heartbeat timeout; do not extrapolate human activity.
- **Simulation state:** clearly show `SIMULATION` banner on the developer preview and mark all simulated location entries. Mock data must never be published to the public/production network feed.

If there are very few concurrent users, consider aggregating or suppressing detailed location/time signals to avoid tracking a person's visit. Design a policy switch such as `public_activity_detail=coarse` and default to coarse in production.

## 7. Interaction scenarios

### Scenario A: Other visitor is currently active

1. Box B's user starts a session, causing an authenticated `session.started` event.
2. Server updates network state and broadcasts `presence.snapshot.updated`.
3. Box A displays `LIVE · Someone is taking a photo in Berlin.` (when appropriate for actual state).
4. Visitor A is encouraged to create a photo.
5. If both sessions remain eligible, matching service creates a `live` match; otherwise it uses the permitted pool fallback.
6. Both active visitors eventually receive the same strip **in the later printing phase**. Current MVP produces one digital test result.

### Scenario B: Photograph taken moments ago

1. Remote capture completes; server emits `portrait.captured` (without image bytes).
2. The local interface displays `RECENT · A photo was just taken in Berlin.`
3. Visitor takes their own picture; eligibility and consent determine whether the earlier portrait can be used.
4. If matched with a stored portrait, explain that this is **not** a live encounter.

### Scenario C: Only an older authorized portrait is available

1. No eligible live participants exist.
2. Pool has one or more valid, consented portraits.
3. Interface shows `Someone left a photo for you.` and a clear `EARLIER` label.
4. When a session begins, match from the pool; never imply that both people are on-site now.

### Scenario D: Single-Pi developer prototype

1. One real Pi captures a consent-authorized test image through the existing CLI.
2. Server emits real local events from real processing state.
3. A browser-based simulator provides virtual remote stations and controlled test events.
4. Developer sees dynamic hero messages, location status cards, and state transitions.
5. Existing mock generation remains usable until the real AI provider is integrated.
6. No touchscreen, speaker, printer, or extra Pi is required.

## 8. Visual design constraints

- Typography-first; clear readable copy at a distance.
- High contrast, uncluttered layout, generous spacing.
- Use a single prominent hero message and a secondary small status panel.
- Color is supplemental: live, recent, earlier and offline must also be distinguished by words/icons.
- LIVE may use a subtle pulsing indicator; RECENT a brief transient ripple; EARLIER a static/archive-style indicator.
- Avoid long decorative animations that delay reading or capture.
- Respect reduced-motion settings in browser preview.
- Support configurable public location names and a flexible list of boxes.
- Desktop browser preview should scale to different kiosk-display aspect ratios in later phases.
- Treat UI content as presentation of authoritative server state, not the source of truth for matching.

## 9. Optional sound (deferred speaker phase)

No speaker support in current MVP. Keep a future-compatible event-to-cue mapping in documentation only:

- `session.started.remote` -> gentle invitation chime.
- `portrait.captured.remote` -> brief camera/shutter cue.
- `match.created.live` -> two-tone connection motif.
- `generation.completed` -> short completion sound.

In a later phase implement user-controlled volume, quiet hours and sound throttling. Sound cues must not imply a live interaction where only pool material exists. No inter-box audio streaming. The microphone is input-only for the new text messaging extension; it does not require a speaker.

## 10. Server architecture and event contract

Introduce a **Social Presence Service** as an independent module, not a replacement for matching or the image-generation worker.

Responsibilities:

1. Consume authenticated events from session, capture and matching services.
2. Derive time-bounded state for each publicly named box.
3. Aggregate a privacy-minimized network snapshot.
4. Publish updates via an authenticated WebSocket or server-sent events channel.
5. Provide a read endpoint for reconnects / browser preview.
6. Apply message-priority rules through a presentation adapter, not in database persistence.
7. Support a simulator transport isolated from the production event channel.

Suggested endpoints (adapt names to existing API conventions rather than duplicating routes):

- `GET /api/v1/presence/snapshot` — aggregate current view.
- `WS /ws/v1/presence` — state changes and short-lived activity notifications.
- `POST /api/v1/dev/simulator/events` — **development-only**, disabled by default and forbidden in production.

Suggested sanitized snapshot:

```json
{
  "type": "presence.snapshot",
  "generated_at": "2026-11-08T11:30:00Z",
  "self_box_id": "box-essen-01",
  "locations": [
    {
      "box_id": "box-berlin-01",
      "label": "Berlin",
      "device_state": "online",
      "activity_state": "session_active",
      "activity_age_seconds": null,
      "match_available": true,
      "simulated": false
    },
    {
      "box_id": "box-london-01",
      "label": "London",
      "device_state": "online",
      "activity_state": "recent_photo",
      "activity_age_seconds": 90,
      "match_available": false,
      "simulated": false
    }
  ]
}
```

All user-facing elapsed-time fields must be calculated from trusted server timestamps, clamped to valid ranges, and refreshed without displaying stale state as live. Do not expose portrait URLs, names, device IP addresses, session tokens or exact participant identifiers in the public snapshot.

**Event types (internal):**

- `device.connected`, `device.heartbeat`, `device.disconnected`
- `session.started`, `session.ended`, `session.expired`
- `portrait.captured`, `portrait.pool_eligible`, `portrait.pool_expired`
- `match.live_created`, `match.pool_created`
- `generation.started`, `generation.completed`, `generation.failed`

Events should carry stable internal IDs, event timestamps and correlation IDs; persist only what is operationally needed. Deduplicate repeated delivery by event ID. Do not broadcast every raw internal event to visitor-facing clients.

## 11. Consent and privacy boundaries

- Explicitly distinguish consent to create an immediate photo strip from consent to keep a portrait in the pool for later matches. The specific mechanism must be reviewed before public deployment.
- In the current no-touchscreen prototype, use consented test images and a documented manual process. CLI capture is not evidence of consent by itself.
- Public displays show only status and messages, never the original portrait, a live image, a face recognition output, or participant identity.
- Revoke or expire portrait eligibility immediately when consent is withdrawn or the retention time ends.
- Disclose activity-signalling in project privacy information; protect very small crowds from visit-time inference through aggregation/coarsening as needed.
- No surveillance-style detection, passive face tracking, hidden camera capture, or location tracking.
- Do not turn social-status logs into a permanent history of identifiable visits.

## 15. NEW — Time-limited live voice-to-text messaging while generating (V0.3)

### 15.1 Experience and scope

**Goal:** During the wait for AI generation, a visitor may talk to the person(s) in the other **currently paired and active** Photobox(es) through short, live text messages. They **do not hear each other** and there is no remote video. Voice is a local input modality only; text appears on the corresponding remote Photobox's screen (or developer browser preview).

The feature is only available when a real **live match** has been established. If the server matched the current visitor with a previously stored portrait, there is no currently present recipient. **Do not** offer messaging in this case, and do not silently route messages to unrelated active boxes. Show a truthful non-interactive message: `Your photo is being created with a portrait from earlier. No one is online in this encounter.`

**Physical prototype:** One Raspberry Pi + USB webcam remains supported. A USB microphone is an **optional hardware addition for this extension**, not a prerequisite for base capture/processing. Enter-key activation can be tested using an attached keyboard or SSH terminal; a real display remains deferred. A browser-based developer preview can display both sides of a simulated matched exchange. For real remote delivery a second live box is required; use a clearly marked two-box simulator until one exists.

### 15.2 Visitor interaction

1. Two **active** visitor sessions become paired (`match.type = live`) and the image-generation job starts.
2. While `GENERATING`, a concise invitation appears: `You're connected to Berlin. Press ENTER to send a short message.`
3. **Press Enter once** to begin recording speech from the Pi's selected USB microphone. Show `Listening…` plus a visible countdown. Use a local recording indicator; never record passively.
4. **Press Enter again** to finish before the time limit, or automatically stop after the configurable maximum utterance duration (suggest **8 seconds** for the first prototype).
5. Run **speech-to-text on the Raspberry Pi**. Provide immediate local feedback (`Transcribing…`, then the recognized text). Send **text only** to the backend, with sender session and live-match identifiers; do not upload or stream audio.
6. The server validates the match, its allowed recipient set, session status, message window, text length and rate limits, then relays the text to the other active paired box(es) over the authenticated status WebSocket.
7. The remote screen/browser preview shows e.g. `ESSEN: Hello from the other side!` as a prominent, short-lived message. The recipient may respond with the same Enter-based flow while generation continues.
8. When the image strip is ready, the message window ends immediately. The result/reveal state takes priority; no new recording can start.

**No microphone?** Hide the voice-action prompt or show `Voice messaging unavailable` in developer mode. Continue photo generation normally. A developer-only text-input simulator may be used to validate routing without speech hardware; label simulation clearly.

### 15.3 Timing and usability rules (configurable defaults, not fixed facts)

| Parameter | Initial prototype default | Rule |
|---|---:|---|
| `message_utterance_max_seconds` | 8 s | Hard recording cutoff per press-to-talk message. |
| `message_window_max_seconds` | 45 s | Hard cap from `generation.started`, even if job runs longer. |
| `message_transcript_max_chars` | 160 | Reject or prompt to shorten oversized messages; do not silently truncate meaning. |
| `message_max_per_sender` | 3 | At most three accepted messages from each sender per match. |
| `message_send_cooldown_seconds` | 3 s | Prevent accidental duplicates/flooding. |
| `message_display_seconds` | 8 s | Message display TTL, unless a higher-priority state replaces it sooner. |
| `message_transcription_timeout_seconds` | 10 s | Fail gracefully if local speech recognition stalls. |

The messaging window closes at the **earliest** of: successful image generation, generation failure/cancellation, configured window deadline, participant exit, loss of live-match eligibility, or explicit session termination. The deadline must be enforced **on the server**, not solely by client UI timers. If generation completes while local transcription is in progress, discard the pending outgoing message without sending it. During printing (later phase), messaging is unavailable by default.

### 15.4 Audio capture and on-device speech recognition

- Capture microphone via a configurable ALSA/PipeWire-compatible Linux input device. Discover and select from connected devices; do not assume a fixed `/dev` index.
- Prefer a small, **offline** speech-recognition implementation suitable for Raspberry Pi (e.g. a locally benchmarked Vosk model or `whisper.cpp` model). Define a `LocalSpeechTranscriber` interface so the actual model can be replaced after accuracy/latency/RAM/CPU tests. Do not claim real-time streaming performance before benchmarking on the actual Pi hardware.
- Aim for **incremental local feedback** where supported, but for the first reliable implementation transmit only finalized, nonempty utterance transcripts after recording stops. Never imply word-by-word remote streaming if the selected engine does not support it.
- Default language configurable (e.g. `en`, `de`); model/language selection should be explicit. If no reliable transcript is produced, display `I couldn't understand that. Try again.` and do not transmit an empty message.
- **Do not persist raw audio**. Keep audio in memory only as long as needed for on-device transcription; release buffers after completion or cancellation. Do not include audio or transcripts in normal application logs.
- Suppress microphone capture when not in the explicit message-recording state. Never start recording due to network events, the photo shutter, or ambient speech.
- Enter-key input must not conflict with camera capture or CLI commands: handle it only in the `GENERATING` + `LIVE_MATCH` + `MESSAGE_WINDOW_OPEN` state. Apply debouncing/keypress handling and ignore key repeats.

### 15.5 Message UI and accessibility

Display only one prominent exchange at a time, with persistent concise context:

- Header: `CONNECTED TO BERLIN · LIVE`
- Subheading: `Your shared photo is being created…`
- Instruction when idle: `PRESS ENTER TO TALK · up to 8 seconds`
- While recording: `LISTENING · 6 seconds left`
- While transcribing: `TURNING YOUR VOICE INTO TEXT…`
- On delivery: `SENT TO BERLIN` (only after server acceptance)
- Received: `BERLIN: See you in the picture!`
- Closed: `Your photo is ready. Messaging has ended.`

Incoming messages must not interrupt the photo pipeline or hijack the consent screen. If an incoming text arrives while the visitor is recording, keep recording indicator visible and queue the incoming text for the next available display slot. Display text with appropriate escaping and line wrapping. Limit stored in-memory received messages to a small capped buffer, and expire them quickly. Provide a future visual-only alternative for visitors who cannot speak; it is not required in the initial one-Pi prototype.

### 15.6 Security, privacy, and message moderation

- Visitor-facing messaging is disclosed before consent to the relevant live session, including **who can receive the text** and its short retention. A voice message must be explicitly initiated by Enter; no ambient listening.
- A match must define an **authoritative set of session/box recipients**; the sender may only reach those participants. No free-form destination, global broadcast, public chat room, or messages to a stored portrait.
- Every incoming message must be authenticated by the box credential and bound to a server-recognized active session and live match. Use a separate message ID for deduplication and acknowledgements.
- Validate Unicode length, normalized whitespace, rate limits, TTL and message type. Sanitize rendering to avoid HTML/script injection. Apply proportionate content filters or moderation rules before public display; blocked texts receive a neutral local error and are not relayed.
- Messages are **ephemeral**, not a permanent social chat archive. Prefer memory-only relay with short bounded TTL (e.g. 60 seconds at most); exclude text from database backups, analytics and raw logs. For debugging, store only status, timings and nonidentifying error codes. Never automatically put transcripts on the printed strip.
- On server disconnect, do not queue voice messages for future delivery to a visitor who may have left. Show `Connection lost. Message not sent.` and require a new deliberate action if reconnection restores an eligible live pair.
- Avoid making the messaging channel a prerequisite for a successful photo strip. Failure of microphone, transcriber or relay never blocks generation or printing.

### 15.7 Server protocol addition

Implement this as a separate **Ephemeral Message Relay** service attached to existing live-match session IDs, not as a new general-purpose chat system.

New server-to-client events (use existing transport/version naming conventions):

- `messaging.window_opened` — server-authoritative match ID and expiry time.
- `messaging.window_closed` — reason (`generation_completed`, `timeout`, `participant_left`, `generation_failed`, etc.).
- `messaging.message_received` — sanitized text, display label, message ID and short expiry; **no audio**.
- `messaging.message_ack` / `messaging.message_rejected` — accepted/rejected with non-sensitive reason code.

Client-to-server event, via authenticated WebSocket or REST according to existing API architecture:

```json
{
  "type": "messaging.send_text",
  "message_id": "8ee5e8b0-92cd-4739-97f1-9a9bcf2dc132",
  "session_id": "session-123",
  "match_id": "match-456",
  "text": "Hello from Essen!"
}
```

Example relay (sender and display labels are verified/derived by the server, not trusted from the client):

```json
{
  "type": "messaging.message_received",
  "message_id": "8ee5e8b0-92cd-4739-97f1-9a9bcf2dc132",
  "match_id": "match-456",
  "sender_label": "ESSEN",
  "text": "Hello from Essen!",
  "expires_at": "2026-11-08T12:00:08Z"
}
```

Do not accept client-supplied `recipient_box_id` as routing authority. The server resolves recipients using the currently valid, live match and enforces the generation window atomically with sending. Use an outbound acknowledgement after successful validation/acceptance; recipient delivery acknowledgement can be separate. Be explicit that accepted is not identical to displayed or read.
